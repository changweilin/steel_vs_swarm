**07-27(二・深夜)手機效能改制:地形解析射線 + 表現層資源回收 + 觸控填充率**(`terrain.js` 新 `rayTerrain`/`markTriDead`、`toon.js` 新 `markShared`/`disposeTree`、`game.js` `_terrainHitT`/`_rayCandidates`/`_entByMesh`/`_takeProjectile`/`_dropBullet`/`_freeEffect`/`_dpr`/`_initScene`/`_pipSources`、`vfx.js` 共用單位幾何 + 傷害數字貼圖快取、`castfx.js` 改用共用 `disposeTree`,新增 `tools/audit_terrain_ray.mjs` / `tools/audit_gpu_lifecycle.mjs`;**純客戶端表現層 ⇒ bal/e2e 天然不受影響,實測仍全綠**):使用者回報「高功耗很 lag,射擊時更 lag,甚至低功耗也會 lag」。三個獨立病灶,不是同一件事:

1. **射擊掉幀的主因 = 每顆子彈每幀對地形做一次逐三角 raycast**。地形是 `TERRAIN.GRID_N` 193² 的高度場 = **73,728 個三角形**,而 three 的 `Mesh.raycast` 是純 JS 線性掃描:包圍球/包圍盒對「射點就在圖內」的射線一律通過,`raycaster.far` **不參與剪枝** ⇒ 一顆 10m 的子彈段照樣掃完整張圖。實測桌機 x86 Node **1.11 ms/條**(手機 ARM 3~6 倍),空中 8 顆子彈 = 一幀 ~9ms(手機 30~50ms)⇒ **純 CPU 成本,調像素比/低功耗完全救不了**,這就是「低功耗也會 lag」的由來。`_resolveAim` 走同一條路,而狙擊導引雷射(`_updateGuideLaser`)**每幀**呼叫它。
   - 修法 = `terrain.rayTerrain()`:Amanatides–Woo 網格行進,只測射線真的穿過的格(子彈一幀 1~4 格 = 2~8 個三角形),**同一組三角形、同一條 Möller–Trumbore ⇒ 命中距離逐條位元級相同**(稽核實測 Δt = 0）。
   - **地雷**:`punchPortalHoles` 會把隧道洞口的三角形從 index 刪掉(彈道要打得進洞),高度場沒有「洞」的概念 ⇒ 打洞時 MUST 同步 `markTriDead()` 記帳,行進時跳過。三角形 → 格的反推**由頂點索引推導**(sorted `v1-v0 === 1` = 上三角 (a,c,b),否則下三角 (b,c,d)),**MUST NOT** 用「第 t 個三角形」推 —— `compact()` 會把 index 就地壓實,序號跟著變。
   - 單位仍走 mesh raycast(命中手感不變),但先過 `_rayCandidates()` 的包圍球廣相(保守外包 ⇒ 命中結果不變,只是不再為射線根本碰不到的目標付逐三角成本)。
