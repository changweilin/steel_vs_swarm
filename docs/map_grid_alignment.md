## 1. 使用者定案(原句)

沒有別的家 —— 這是所有取捨的上游,改設計前先回來讀一次。

**第一輪**
> 「處理圖資時先找出地圖上下左右對準哪一個方向時,可以對齊最多的大馬路組成正交網格,接著將
> 所有道路量化成 16 個方向,同時盡可能避免讓道路變成鋸齒,這樣道路拼圖可以透過這 16 個方向
> 簡化並無縫準確貼合對齊,建築也更容易對齊排列。」

追問「是真的把世界轉過來,還是只用那個角度當 16 方向的錨?」→ 定案 **真的旋轉整張地圖**;
量化對象定案 **只有 `osmRoads`**(鐵路/兵線/建物輪廓皆不動)。

**第二輪**
> 「圖資儲存在開房者,再由開房者透過 server 傳給入房者?」

## 2. 已排除的選項(附排除理由;**不要重新提案**)

| 選項 | 排除理由 |
|---|---|
| 只把 θ 當「16 方向的錨」,世界不轉 | 使用者第一輪明確選了「真的旋轉整張地圖」 |
| θ 在**建圖期**由各客戶端自己算 | `startPrebuild` 是每台各跑一次的,而 `scheduleOsmRetry` 的存在就證明「這一輪 Overpass 被限流」是常態 ⇒ A 抓到 θ=−29°、B 沒抓到 θ=0,兩台整個世界差 29°。今天的 miss 只讓那台少幾座橋(局部);θ 的 miss 會讓所有座標對不上(全域)|
| 用**已在手上的兵線**估 θ(零網路) | 實測 58 組對比大馬路烘焙值:p50 3.9° / p75 8.8° / **p90 16.1° / max 44.0°**,落在半格內只有 79%。最差是整個轉錯(barcelona L1 估 −15° vs 真值 42.8°、iguazu L3 差 44°),而且**同一張圖會隨人數轉不同角度**(shibuya L1/L3/L5 = −6.3°/27.8°/29.7°)⇒ 直接出局 |
| 事後把「短方向段併進鄰段」來去鋸齒 | 它把 DDA 排好的階梯併回單一方向 ⇒ 長度重解退化成「兩錨點之間拉直」= 那條路等於沒被量化。實測拿掉併段後誤差 p90 由 5.9° 掉到 0.5°,而直段均長只從 122m 降到 86m。**已寫成 A42 ⑥ 禁令** |
| 讓量化不受位移上限、把路整條吸到鄰格 | 卡在格界(11.25°)的 1.5km 直路尾端會甩出 **518m**(實測),那條路就此離開衛星底圖、離開已整平的路基、離開自己那條兵線 |
| 自訂地圖的 θ 在 **mapSelect 掃描階段**量 | 掃描時 `center` 還沒定案(它是錨點 A 與**所選候選點** B 的中點)。改在「存入最愛」那一次量 —— 手動地圖一定要存成最愛才開得了房 ⇒ 涵蓋 100%,而且一樣是一次性、使用者主動觸發、輸出直接進 battleConfig |
| 中繼 payload 降到 6 位小數(可砍半)| `DP = 7` = OSM 原生精度 ⇒ 淨化對真圖資是**恆等**;降到 6 位會讓「開了中繼」與「中繼逾時退回自己抓」建出兩張略微不同的地圖 —— 小到剛好測不出來,而破圖照樣發生。payload 用不著省(1.05MB / 2MiB)|
| 中繼下來的路網寫進入房者的 geocache | 來源是房主 = 不可信輸入。持久化會污染這台機器**之後每一場**(含它自己當房主那一場),而 geocache 的紀律正是「只准存自己完整抓到的東西」。代價只是「下一場還要等一次中繼」,而中繼很快 |

## 3. 還沒驗(㋕ 真機 / 兩台機器)

離線與 ㋓ 的部分已經全部跑完(清單見 PR #188)。剩下的都是**單機與單一客戶端永遠測不到**的:

- **路網中繼的兩台同房實測** —— 一台開房、一台入房,比對橋隧與建物是否逐項一致。壞掉的症狀是
  「你說的那座橋我這邊沒有」。同場再看「房主被限流、90 秒後補抓成功」那條路徑:入房者要在
  **房間階段**自動重建成同一份。
- **自訂地圖主方位走一次** —— 地圖上手動點選 → 存入最愛(這時多發一次 Overpass)→ toast 印出角度
  → 開房建圖真的轉了。離線稽核只驗得到接線與紀律,驗不到「畫面真的轉了」。
- **看一張旋轉過的市區圖** —— 建議 manhattan 或 barcelona(主方位大、效果最明顯)。

**與本題無關的既有紅字**(已在 main 上覆核,不要誤修):`audit_touch_layout` 667×375 橫式在 main
上就是紅的;`audit_lane_grade_sep` 在此 worktree 缺 `tools/.osm_cache` 而拋 ENOENT。

## 4. 還沒決定 / 待觀察

- **`audit_venue_biome` Ⅲ:12 個場地的手寫 `mix` 與圖資實測不符**(yangmingshan / aokigahara /
  blackforest / giza / uluru / phoenix / hehuanshan / venice / iguazu / tamsui / okavango / rio)。
  與旋轉那三輪無關(它讀的是 `mix`/`type`,那兩欄沒動過),CI 也只收 `--offline` 那一半;
  該支檔頭自陳 `TOL` 是「挑出該看的圖,不是判死」。**要不要調 `mix` 是使用者的決定。**
- **`audit_traverse` 的 21 條既有紅字**(橋面中段不可達 / 橋下淨空 / taroko 隧道)。已證明旋轉前
  是 26 條、種類一條沒變 ⇒ 是稽核端的泛洪/夾制議題,不是遊戲破圖。四個成因與診斷法見
  `traverse-audit-baseline-reds` 記憶與該支檔頭。**修它是獨立題目。**
- **舊的「我的最愛」維持 `rot = 0`**(刻意不追溯量測):要補就得在開戰時刻畫面再加一次網路依賴,
  換來的只是舊存檔轉個角度。
- **中繼沒有進度回饋**:入房者等中繼時,預載狀態列顯示的仍是模型/地形進度。等待與地形建構並行
  ⇒ 一般看不出來;只有房主整組失敗時入房者會多停最多 20 秒而畫面沒說明。
- **中繼 payload 餘裕不厚**:實測 5v5 密市區 1.05MB ⇒ `maxPayload` 餘裕 1.9×、`MAX_BYTES` 1.6×,
  而 OSM 只會長大。這是待觀察不是待辦 —— 下次動這一族 MUST 重跑 `tools/measure_osm_relay.mjs`
  (它的查詢字串取自 `biomes.js` 執行原文,不會靜默過期)。
- **`civicblvd` 的 `relief: 27`**:重烤那一輪的實測是 `null`(側翼幾乎全落在橋/洞段,而那些要扣掉),
  而稽核對 `peakSide == null` 刻意不判(分不出「這次沒量到」與「量到就是沒有」)⇒ 舊值留著。
