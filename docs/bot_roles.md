# 電腦玩家定位分類與策略(bot roles)

> 2026-08-08 使用者需求:「幫依機體技能等數值為電腦玩家分類,並設計不同策略」。
> 本文是設計定案與操作手冊;縫的索引見 `CLAUDE.md §2.1`,逐項斷言見 `tools/audit_bot_role.mjs`。
> 學習迴圈那一半見 [`docs/bot_learning.md`](bot_learning.md)。

## 0. 一句話架構

**機體自己的數值決定它屬於哪個定位,定位決定它把 `BOT_TACTIC` 的哪幾個旋鈕往哪邊調** ——
分類與策略都是推導出來的,沒有任何一行「s01 是突襲型」。

```
 data.js 的平衡數值(武器 / 機體 / 招式)
        │  HEX_AXES[].val(圖鑑六角圖那六軸的同一份取值)+ buildDps + heroAbility
        ▼
 botRoleFeats(ch)  七項特徵,各自 0~1(對數分位:相對全場的位置)
        │  Σ w·(特徵 − 0.5) 取 argmax
        ▼
 botRoleOf(ch) → 突襲 / 壓制 / 攻堅 / 支援
        │  botRoleTactic(基準表, 定位):11 個旋鈕 × 正規化後乘數 → 夾制 → botTacticCross
        ▼
 server/bots.js  BotBrain._resolveRole()(唯一解析縫)→ this.tac(唯一讀取縫)
```

改任何一個平衡數值,圖鑑的六角圖與 bot 的定位**同步**改 —— 這就是「依機體技能等數值分類」
這句話能長期成立的原因。

## 1. 為什麼要分類

改制前,32 台機體的 bot 共用**同一張** `BOT_TACTIC`:同樣的距離環、同樣的選敵權重、同樣的
撤退線、同樣的採購順序。一台 6.4 m/s 的偵察無人機與一台扛 26 護甲的攻城機甲用一模一樣的
打法 —— 而那張表只可能對其中一種是對的。

這件事**沒有錯誤訊息**,只表現成「這台 bot 好像不太會用自己的機體」:高機動短射程的機體站在
射程外磨、重甲攻城機在塔的射程邊緣猶豫、專職治療的機體衝到最前面被秒。

## 2. 七項特徵(`BOT_ROLE_FEATS`)

| 特徵 | 取值來源(唯一縫) | 為什麼是它 |
|---|---|---|
| `dur` 耐久 | `HEX_AXES.dur.val`(裝甲 HP + 護盾) | 能不能站著換血 |
| `armor` 護甲 | `HEX_AXES.armor.val` | 同上,但吃的是減傷不是血量 |
| `fire` 火力 | `HEX_AXES.fire.val`(輕 + 重持續 DPS) | 交戰窗要多長 |
| `zone` 制域 | `HEX_AXES.zone.val`(射程 × 打擊足跡等效直徑) | 一發能否定掉多大一塊空間 |
| `mob` 機動 | `HEX_AXES.mob.val`(壓縮後移速) | 追得上 / 逃得掉嗎 |
| `siege` 攻堅 | `buildDps(ch, 光) + buildDps(ch, 重)` | 值不值得停下來拆塔 |
| `aid` 支援 | 兩個招式槽的團隊供輸比例 | 這台機體的招式是打人還是養人 |

三條紀律:

- **取值一律轉呼既有唯一縫**。在這裡自己算一份 DPS/EHP,症狀是「圖鑑上看起來是這樣、bot
  打起來不是」,而兩邊都看不出錯。
- **前六項取對數分位**(同 `hexBand`:差幾倍決定位置,不是差多少)。絕對值沒有可比性 ——
  「射程 190」在輕武器裡是最遠、在重武器裡是最近。
- **`aid` 刻意不取分位**:它本來就是 0~1 的佔比,取分位會把「一招都沒有」與「有一招」拉成
  0 與 1 的二元旗標。
- 六角圖的 `power`(電力)**不收**:它決定「多久放一次招」,不是「該站多近、該先打誰」。

## 3. 四個定位(`BOT_ROLES`)

分數 = `Σ w_i × (特徵_i − 0.5)`,取最高者。**特徵置中**是公平性的來源:各項都恰好中庸的機體
對四個定位一律得 0 分,不會因為某個剖面正權重比較多就先天佔便宜;`Σ|w| = 1` 讓四個分數落在
同一把尺上。兩條都由稽核釘住。

| 定位 | 判別剖面 | 策略主軸 |
|---|---|---|
| **突襲** `raider` | 機動高、扛不住、單體 | 貼身點殺、撿尾刀、獵殺輸出核心;見血就退、退得近(跑得回來) |
| **壓制** `zoner` | 制域大、火力高 | 站中距離讓範圍發揮,不追人也不主動貼臉 |
| **攻堅** `siege` | 耐久護甲高、對建築 DPS 高 | 咬工事、貼著塔打,撐到裝甲見底才脫離 |
| **支援** `support` | 招式在供輸隊友 | 站最後面、最早放招、最早脫離(死掉的支援供輸為零) |

現役名冊由 `node tools/audit_bot_role.mjs` 最後一段印出來(2026-08-08:突襲 9 / 壓制 11 /
攻堅 9 / 支援 3)。**名冊會隨平衡調整自己位移,這是特性不是 bug** —— 一台被砍掉火力的機體
本來就該換一種打法。要看誰換了打法,跑那支稽核比對前後兩份名冊。

## 4. 策略 = 旋鈕覆寫,不是第二套決策系統

定位只改 11 個旋鈕的值 + 八軌採購順序;`bots.js` 的狀態機、選敵流程、撤退流程**一行都不動**,
也不准出現任何 `if (role === 'siege')` 的行為分支。

| 旋鈕 | 基準 | 語意 |
|---|---|---|
| `KITE_NEAR` | 0.55 | 打帶跑:可擊發時的距離環(高難度) |
| `KEEP_F` | 0.6 | 沒有打帶跑時的一般距離環 |
| `KEEP_STRUCT` | 0.85 | 打建築的距離環 |
| `W_OUTPUT` / `W_EXEC` | 0.7 / 1.0 | 選敵:敵方輸出核心 / 快陣亡目標 |
| `PRIO_HERO` / `PRIO_STRUCT` | 0.55 / 1.3 | 選敵加權距離:英雄折扣 / 工事加價 |
| `PULL_HP` / `PULL_SP` | 0.32 / 0.5 | 撤退線:裝甲門檻 / 護盾門檻 |
| `RALLY_BACK_M` | 70 | 集結點退到塔後多遠 |
| `CAST_HURT` | 0.55 | 自保/輔助招式的觸發血線 |

後五個旋鈕是這一輪從 `bots.js` 的硬編碼常數收上來的,**基準值逐一等於改制前那幾個數字** ⇒
沒有定位覆寫時逐位元同舊制。

### 4.1 覆寫是重分配,不是通膨

每個旋鈕的四個乘數以**角色數加權的幾何平均 = 1** 正規化(`botRoleNorm`,同
`AOE_BUDGET.NORM` / `SPEED_COMP` / `BUILD_DPS` 的同一條)⇒ 全體 32 台的該旋鈕幾何中點
**逐位元錨在使用者定案的基準值上**。

少了這一步,「給每個定位一點加強」會變成整批 bot 悄悄變強或變弱 —— 而 `npm run sim` 的勝負
旗標對這種整體漂移是飽和的(量不出來)。稽核把這條當核心不變式,`--break-norm` 是它的反例。

寫在 `BOT_ROLES[r].mul` 的是**相對**乘數,正規化不改變定位之間的兩兩比值(稽核釘住)——
所以調整時只要想「這個定位相對別人該更貼還是更退」,水位自己會回到基準。

### 4.2 夾制與交叉約束

覆寫後逐鍵夾到 `BOT_ROLE.KNOBS` 的合法域,再過 `botTacticCross`(與學習夾制
`botPolicySanitize` **同一支**):`W_THREAT` 恆最重、`KITE` 近 < 遠、`PULL_HP > BASE_HP`。
與學習白名單重疊的旋鈕,定位邊界 MUST 收在學習邊界之內(稽核反查)。

夾到邊界的項目由稽核逐項印出來 —— 靜默截斷等於「這個定位的乘數是推導的」對它其實不成立。
2026-08-08 有兩項:攻堅的 `PRIO_STRUCT`(0.943 → 1.000:定位最多把工事加價收到「不加價」,
**MUST NOT 變成優先拆塔** —— 把塔排在英雄/小兵之前會讓 bot 站在塔下被集火)與攻堅的
`PULL_HP`(0.279 → 0.300:低於 `BASE_HP` 就直接回堡了,RALLY 那一段會變死碼)。

## 5. 與難度分層、學習迴圈的關係

- **難度**(A33):定位覆寫只在 `BOT_DIFF.tactic` 之下解析 ⇒ 新手/低難度**結構性地**逐位元
  維持舊制,不靠「記得別改到」。
- **學習**:`bot_learn` 學的是全體共用的**基準**(`BOT_LEARN.KEYS` 那 8 鍵),定位是疊在那份
  基準上的相對偏移。**刻意不為四個定位各學一份**:搜尋空間 ×4、每一份的樣本數 ÷4,而
  `docs/bot_learning.md` 已經量過,單場工事損血在 433~10298 之間跳 —— 訊號會整個淹在雜訊裡。
  五個新旋鈕因此**不進**學習白名單,`botPolicy.js` 與平衡指紋逐位元不受這一輪影響。
- 解析點在 `update()` 而不是建構函式:學習迴圈是在**構造之後**才注入基準策略
  (`b.tac = candTac`),在建構函式裡定案會被那一行整份蓋掉。

## 6. 操作

```bash
node tools/audit_bot_role.mjs                # 80 項;最後一段印出現役定位名冊
node tools/audit_bot_role.mjs --break-role   # 四個剖面同形 ⇒ Ⅰ 紅字
node tools/audit_bot_role.mjs --break-norm   # 乘數不正規化 ⇒ Ⅱ 紅字
node tools/audit_bot_role.mjs --break-tier   # 低難度也套定位覆寫 ⇒ Ⅳ 紅字
```

調整定位策略時:改 `BOT_ROLES[r].mul` 的**相對**乘數(水位自己回到基準),跑上面那支稽核,
再照 `CLAUDE.md §5`「電腦玩家改動的退化量測法」量一次 —— 判準是繞行% / engage% 這類結構性
指標,**不是** `npm run sim` 的勝負旗標(二元訊號在長局天生飽和)。

## 7. 落地量測(2026-08-08 基準)

作法:**定位版 vs 關掉 `_resolveRole` 的同一批 bot**(= 改制前行為),CRN 配對鏡射自對戰
(每顆種子跑「定位版當 SWARM」與「當 STEEL」各一場),高難度 3v3 × 600s × 28 場。

| 指標 | 定位版 | 對照組(改制前) |
|---|---|---|
| 適應度(工事損血差 + 擊殺差) | **+0.35**(SD ≈ 1.55、SE ≈ 0.29) | 0(定義) |
| 工事損血 造成 / 被打 | 3204 / 2604 | — |
| 擊殺 | 2.0 | 1.6 |
| engage% | 21.3% | 20.1% |
| RALLY% | 11.5% | 12.8% |
| RETREAT% | 19.0% | 16.5% |
| 繞行% | 1.5% | 2.0% |

**結論:沒有退化,略為變強但落在雜訊內**(t ≈ 1.2,28 場配對仍不到 95% 顯著)。要判「有沒有
壞掉」看的是結構性指標而不是適應度:繞行% 1.5% < 2.0%(沒有多出卡住的 bot)、engage% 略升、
RALLY% 略降(沒有卡在撤退)。RETREAT% 從 16.5% 升到 19.0% 是**預期**的 —— 突襲/支援兩個定位的
`PULL_HP` 本來就被推高(見 §4 的設計主軸),而攻堅型相對更晚才脫離。

這一輪**不是**為了讓 bot 變強,是為了讓每台機體用適合自己數值的打法;整體水位由 §4.1 的
正規化錨住,所以「總體差不多、個別打法明顯不同」正是預期的形狀。
